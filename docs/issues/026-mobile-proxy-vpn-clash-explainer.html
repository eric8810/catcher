临时说明页 iOS / Android / Electron

开了代理后，HTTP 和 WebSocket 都连不上

现在更准确的判断是：旧链路能用，Clash escape 也能让 App 直连，说明手机和服务器本身不是完全不通。修复前 Catcher 接手后全断，最可疑的是 Catcher 在真正连接服务器之前，已经自己做了 DNS 或自己建了连接，导致 Clash 没机会按原规则处理。

第一怀疑：DNS 先失败 修复前 Catcher HTTP / WS 都会先用自己的 DNS resolver，请求可能还没到连接阶段。
第二怀疑：规则上下文变了 域名被提前解析成 IP 后，Clash 的域名、fake-ip、分流规则可能不再命中。
第三怀疑：没走代理流程 修复前 HTTP 没传 proxy，WebSocket 也没有 CONNECT / SOCKS5 连接流程。
网络切换没重建 代理或 VPN 开关后，旧连接池、旧 DNS 缓存、旧 WS 连接还可能继续用。

为什么 Clash escape 也救不了

关键不是“escape 无效”，而是 Catcher 改了前半段链路

escape 要生效，Clash 至少要看到 App、域名、fake-ip 或连接目标。如果 Catcher 自己的 DNS 先失败，后面就没有业务连接；如果 Catcher 先把域名变成真实 IP，Clash 看到的内容已经和旧链路不同，规则可能就匹配不上。

最可能：Catcher DNS resolver 和 Clash / 系统 DNS 不一致。
其次：HTTP / WebSocket 没按当前代理或 VPN 路径建连接。
再看：VPN 或 Clash 开关后，旧 DNS 缓存和旧连接池没有重建。
旧链路
App → 系统网络栈 → Clash 判断 → escape 直连 → 服务器。 这条路能用，说明 Clash 能识别原来的 App 请求和域名。
Catcher
App → Catcher DNS → 解析失败或拿到真实 IP → 再尝试连接。 这时可能还没发出 HTTP / WSS 连接，也可能让 Clash 失去原来的规则判断依据。
结果
表现就是“什么请求都发不出去”。 这不等于服务器不可达，更像是请求卡在 DNS、代理选择或连接建立之前。

责任边界和验证项

Catcher 已做

  • DNS 策略显式化。不配置 dns 时使用原生解析；显式 dns.mode = catcher 才启用 Catcher DNS。
  • 不再静默退回 Google DNS。读取系统 DNS 失败时默认报错，只有显式打开 fallback 才退回默认 DNS。
  • HTTP 和 WS 共用网络配置。代理、DNS、TLS、网络路径版本都已暴露给两条链路。
  • WS 补齐代理能力。WS 现在走 yawc + reqwest，复用 HTTP CONNECT、SOCKS5、SOCKS5 远端 DNS。
  • HTTP 补齐真实 SOCKS 能力。已启用 reqwest socks feature。
  • 网络变化后可重建。已暴露 network_path_id，外部在 VPN / Clash / DNS 变化时传新值并重建 client。

外部集成要做

  • 平台探测。echoo 读取 iOS / Android 的 VPN、代理、DNS、网络变化；klip 用 Electron session 查询目标 URL 的代理结果。
  • 传入统一配置。HTTP 和 WS 都使用同一份 proxy、DNS、TLS、networkPathId。
  • 网络变化后重建。Clash、VPN、系统代理、Wi-Fi、蜂窝变化后，重建 Catcher HTTP / WS client。
  • 保留业务边界。应用层只管 token、ready、业务消息；连接、代理、DNS、TLS 交给 Catcher。
  • 分别落文档。echoo 和 klip 的接入工作已写到各自项目的 docs/issues 目录。

继续定位的验证项

  • 看 DNS 是否先失败。记录 DNS 模式、nameserver、解析结果、耗时和错误。
  • 确认默认原生解析是否恢复。不传 dns 时应按系统 / reqwest 默认路径解析。
  • 对比解析结果。比较旧链路、系统 DNS、Catcher DNS、Clash fake-ip 的差异。
  • 确认有没有 TCP 连接。如果没有连接日志，就不是服务器拒绝，而是连接前失败。
  • 看 Clash 和服务端日志。确认 Clash 是否看到连接、服务端是否收到请求。
  • 再查 TLS。只有 DNS 和 TCP 都成功后，才优先看证书和 WSS 握手；WS pinning 仍是后续项。

两条路的差别

系统期待的路

应该这样
1 App 发请求 HTTP / WSS
2 系统网络策略 VPN / Clash / 代理
3 目标服务 由代理或 VPN 转发
DNS 按当前网络解析 可能由 VPN 或代理处理
关键点：先问系统当前网络怎么走，再决定 DNS、代理、证书和连接。

Catcher 现在的路

容易失败
1 App 发请求 Catcher 接手
4 目标服务 被尝试直连
2 Catcher 自己建连接 没拿到系统代理
3 本地 DNS 可能绕过代理策略
VPN Clash / VPN 没有被正确使用
失败点：HTTP 没进代理，WebSocket 也没进代理；DNS、证书和网络变化也没有统一处理。

修复前 HTTP 和 WebSocket 都连不上的四个原因

1

HTTP 没拿到代理

用户开了 Clash，本地代理可能是 127.0.0.1:7890。Catcher HTTP 没拿到这条信息，就不会先进代理，而是按默认方式直连。

2

修复前 WebSocket 没有代理通道

WSS 也需要先连代理，再 CONNECT 到目标，再 TLS 握手。修复前 WS 是解析目标 IP 后直连，代理规则自然失效。

3

DNS 和代理顺序反了

很多代理希望拿到域名后自己解析。修复前 Catcher 先本地解析成 IP，可能破坏 fake-ip、远端 DNS 和分流规则。

4

网络变了但连接没换

VPN 开关会改变路由和 DNS。旧连接池、旧 DNS 缓存、旧 WS 连接如果继续用，就像拿旧地图找新路。

本次修复后的结构

外部项目平台探测 VPN、系统代理、PAC、证书、网络变化
统一网络配置 把当前网络规则变成统一配置
Catcher 核心 统一处理代理、DNS、TLS、重建
HTTP Transport HTTP / HTTPS / SOCKS5 / DNS 策略
WS Transport CONNECT / SOCKS5 / WSS TLS / 重连

已做 1：HTTP 和 WS 用同一份网络策略

两条链路都已暴露 proxy、DNS、TLS 和 networkPathId。

已做 2：代理场景不提前乱解析 DNS

不配置 dns 时走原生解析；使用 socks5h 时把目标域名交给代理解析。

已做 3：VPN 或代理变化后可重建连接

外部项目传入新的 networkPathId，并重建 HTTP / WS client。

已做 4：证书配置主要能力对齐

HTTP 和 WSS 都支持自定义 CA、证书校验开关；WS pinning 后续单独补齐。

最短解释

用户开 VPN 或 Clash，不是网络真的没了。 网络只是换了一条规则：HTTP 要进代理，WebSocket 也要进代理，有些 DNS 要交给代理，有些连接要跟随 VPN。Catcher 现在已经补齐了 HTTP / WS 的统一代理、DNS、TLS 配置入口；外部项目还需要把平台当前网络状态传进来，并在网络变化后重建 client。
